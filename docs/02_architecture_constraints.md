# 아키텍처 제약 — 나중에 못 고치는 것들

> 여기 적힌 것은 취향이 아니라 **제약**이다. 1차 첫 커밋부터 지켜야 하고, 나중에 부착하려면 전 코드를 다시 만져야 한다.

## 1. 감사로그 · 접속기록은 데이터 접근 계층의 산출물이다

### 왜

건강정보 = **민감정보**다. 「개인정보의 안전성 확보조치 기준」상 개인정보처리시스템 접속기록은 최소 1년, **민감정보·고유식별정보를 처리하면 2년** 보관하고 **월 1회 이상 점검**해야 한다.

### 어떻게

핸들러마다 `logAudit(...)`를 호출하는 구조로 만들면 **반드시 빠뜨린다.** 리포지토리(또는 ORM 훅 / 미들웨어) 한 곳에서 자동 기록되게 한다.

```
repository.update(table, id, patch)
  ├─ before = select(table, id)
  ├─ 실제 UPDATE
  └─ audit_log.insert({actor, ip, action:'update', table, id, before, after})
```

- 기록 대상: `create` / `update` / `delete` / `publish` / `export`
- `actor`는 요청 컨텍스트(인증 미들웨어)에서 주입한다. 리포지토리가 인자로 받게 하면 또 빠뜨린다.
- **회원의 건강정보를 조회하면 `access_log`에 별도 기록**하고, 관리자에게는 **열람 사유 입력을 강제**한다.
- 두 테이블은 **append-only**. 애플리케이션 코드에 UPDATE/DELETE 경로를 만들지 않는다.

### 체크리스트

- [ ] 관리자에서 데이터를 바꾸는 모든 경로가 `audit_log`에 남는가
- [ ] 회원 건강정보 조회가 `access_log`에 남고 사유가 기록되는가
- [ ] 두 로그를 조회하는 화면(adm_028)이 있고 CSV로 내보낼 수 있는가
- [ ] 월간 점검 기록(`audit_review`)을 남길 수 있는가

## 2. 권한은 라우트 진입 지점에서 일괄 검사한다

### 왜

화면마다 개별로 검사하면 새 화면을 추가할 때 빠진다. 그리고 **개인정보 열람 권한은 콘텐츠 편집 권한과 분리**되어야 한다 — 콘텐츠 에디터가 회원 건강정보를 볼 수 있으면 안 된다.

### 어떻게

`admin_permission(role_id, resource, action, allowed)` 매트릭스를 두고, 라우트 정의에 `resource`와 `action`을 선언한다.

```
route('/admin/members/:id', { resource: 'adm_015', action: 'pii_read' })
route('/admin/nutrients',   { resource: 'adm_022', action: 'write'    })
```

`action`은 `read | write | delete | publish | **pii_read**` 다섯 가지. `pii_read`는 별도 축이며 `write` 권한이 있다고 자동으로 따라오지 않는다.

### 체크리스트

- [ ] 권한 검사가 라우트 미들웨어 한 곳에 있는가 (핸들러 내부가 아니라)
- [ ] `pii_read`가 다른 권한과 독립적으로 부여되는가
- [ ] 권한 없는 접근이 감사로그에 남는가

## 3. 판별 API는 어댑터 뒤에 둔다

준차트 스펙이 아직 없고 일정도 외부에 달려 있다. **1차 전체가 mock으로 완결되어야 한다.**

```
interface DiagnosisProvider {
  submit(answers): Promise<{ raw: number }>   // 1~64
}

MockDiagnosisProvider      // 1차. 임의 1~64 + 인위적 지연(로딩·타임아웃 UI 검증용)
JunchartDiagnosisProvider  // 2차. 실연동 시 이것만 추가
```

- 어느 것을 쓸지는 `app_config['diagnosis.provider']` 설정으로 결정한다.
- **결과를 소비하는 코드가 준차트의 존재를 알면 안 된다.** `raw` 정수와 `status`만 안다.
- 실패·타임아웃 경로를 mock에서도 재현할 수 있게 만든다(sc_009a의 재시도 UI를 1차에 검증해야 함).

### 문진 문항도 마찬가지

문항은 외부에서 받는다. 1차는 고정 목록(fixture)으로 렌더링하고, 수신 인터페이스만 정의해 둔다. **관리자에 문항 CRUD를 만들지 않는다**(adm_004/005는 보류).

## 4. 민감정보 취급

- **문진 응답 원문을 보관할지 먼저 결정한다(📌).** 보관하지 않아도 된다면 `diagnosis_result`에 결과값만 남기는 쪽이 훨씬 안전하다. 1차 기본값은 "결과값만".
- 건강정보 동의는 **다른 동의와 통합할 수 없다.** `consent_item.is_sensitive = 1` 항목은 가입 화면에서 별도 체크박스로 렌더링한다(sc_092).
- **만 14세 미만 가입 불가.** 자기신고 체크 미충족 시 진행 차단.
- 보유기간은 `retention_policy` 테이블 값으로 배치가 돈다. **처리방침 문안과 이 테이블 값이 어긋나면 안 된다.**
- **비로그인 문진(§6 참조)에서는 응답을 서버에 저장하지 않는다.** 클라이언트(브라우저)에만 들고 있다가, 로그인+약관동의가 끝나는 시점에 한 번에 전송해 `diagnosis_result`를 생성한다. 동의 없이 개인정보를 먼저 모아두는 상태를 만들지 않기 위함이다.
- **예외 — `diagnosis_stat`(설문 편향 분석용 익명 집계)는 로그인 여부와 무관하게 즉시 기록한다(2026-07-31 결정).** `type_id`+`day` 카운트만 쌓고 user_id·IP·정확한 시각 등 식별자를 절대 포함하지 않는 조건에서만 예외다. 식별자가 하나라도 섞이면 그 순간 개인정보가 되므로 위 원칙(동의 전 미저장)으로 돌아간다.

## 5. 되돌릴 수 없는 기능은 만들지 않는다

트래커·무드·케어포인트는 보류다. 이유는 개발량이 아니라 **한 번 사용자 기록이 쌓이면 지울 수 없기 때문**이다.

- 해당 테이블을 **미리 만들어 두지도 않는다.** 빈 테이블은 "곧 붙일 것"이라는 신호가 되어 범위를 되살린다.
- 도입이 결정되면 구조는 이미 정해져 있다: `daily_log(user_id, date, axis, value, source)` **세로 한 테이블**, `axis`는 공통코드. 축마다 컬럼을 만들지 않는다.

## 6. 문진은 로그인 없이 시작한다 (2026-07-31 추가)

### 왜

체질 결과를 카카오톡으로 공유받은 사람이 문진을 시작하기까지 **로그인이라는 문턱**이 있으면 유입이 죽는다. 그래서 순서를 뒤집었다: **문진 → 결과 티저 → 그때 가서 가입.** "일단 궁금하니까 풀어본다"가 먼저고, 가입은 결과를 마저 보고 싶어질 때 요구한다.

이 순서는 공유링크로 들어온 사람만이 아니라 **홈 화면에서 스스로 들어온 사용자에게도 동일하게 적용**한다.

### 어떻게

```
스플래시(sc_090)
  → 문진 유도(sc_004a) → 문진 설명(sc_008) → 문진 진행(sc_009) → 결과 대기(sc_009a)
  → 결과 티저(sc_010) ─────────────────────── ★ 아직 비로그인 상태
      · 체질 유형명/별명만 노출, '자세히 보기' 버튼
      · 이 시점의 판별 결과는 `diagnosis_result`에 저장하지 않는다(§4). 클라이언트가 raw_value를 잠깐 들고 있는다.
  → '자세히 보기' 탭 → 로그인(sc_091) + 약관 동의(sc_092, 민감정보 별도동의 포함) + 접근권한 안내(sc_093)
  → 가입 완료 시점에 raw_value + 문진 응답을 서버로 전송 → diagnosis_result 생성
  → 결과 상세(sc_004b) + 건강신호(sc_005) + 예측질환(sc_006) → 처방 스트림(sc_007…)
```

- **mock 판별 API는 비로그인 상태로도 호출 가능해야 한다.** `DEFAULT_PERMISSION_CLASSES = IsAuthenticated`가 기본값이므로(`docs/08_tech_stack.md` §5), 이 엔드포인트만 명시적으로 `AllowAny`로 열어둘 것 — "빠뜨려서 열리는 것"이 아니라 "의도적으로 연 것"임을 코드에서 분명히 한다.
- **카카오 공유 시 링크 미리보기(OG 이미지·제목)**는 문진 유도 화면(sc_004a) URL에 표준 OG 메타태그를 붙이면 된다. 체질별 맞춤 공유 이미지(64종)는 2차 이후 별도 결정(§ 아래 📌 목록 참조).
- sc_010은 기존 명세의 "결과에 대한 간단한 1차 안내" 역할 그대로이며 화면을 새로 만들 필요는 없다. **위치만 로그인 이전으로 이동**한 것.

## 7. 콘텐츠는 약점 태그로 흐른다

고객 처방 화면 내용은 체질별 수동 큐레이션이 아니라 **체질 → 약점 태그 → 콘텐츠** 자동 조회다.

```
tem_type → tem_type_weakness → weakness
                                  ├─ nutrient_card_weakness → nutrient_card → nutrient
                                  ├─ food_weakness          → food (polarity: 권장|제한)
                                  ├─ article_weakness       → article (+food/point/product)
                                  └─ herb_card_weakness     → herb_card → herb
```

예외는 `tem_type_curation`(영양·약재·식품군의 체질별 노출 선택)뿐이다. 여기서 `ref_id`는 **카드 id**(nutrient_card / herb_card)이고 식품군만 food id다.

**약점 태그가 없는 콘텐츠는 고객 화면에 절대 나타나지 않는다.** 관리자에서 약점 선택을 필수로 강제할 것.

## 8. 커밋 전 확인

- [ ] 새로 추가한 데이터 변경 경로가 감사로그를 남기는가
- [ ] 새 라우트에 `resource`/`action`이 선언되었는가
- [ ] 명세서에 없는 화면·필드를 임의로 추가하지 않았는가
- [ ] `단계 = 보류`인 기능의 테이블·코드를 만들지 않았는가
- [ ] 준차트를 직접 참조하는 코드가 어댑터 밖으로 새지 않았는가
- [ ] 비로그인 문진 응답이 가입 전에 서버(DB)에 저장되지 않는가
- [ ] 비로그인으로 열어둔 엔드포인트가 딱 그 목적(mock 판별 실행)에만 쓰이는가 — 다른 개인정보 API가 같이 열리지 않았는가
